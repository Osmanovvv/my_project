# Security review 9.16

Дата проверки: 2026-10-13  
Область: локальный исходный код, production-shaped build, Docker/systemd/Nginx
конфигурация и автоматические проверки этапа 9.

## Результат

Критических обходов авторизации, утечек секретов или неконтролируемой отправки
сообщений в локальной реализации не обнаружено. Шаг 9.16 выполнен локально.
Проверка production-сервера и реального Telegram API остаётся отдельной частью
развёртывания.

В ходе review дополнительно закрыты два риска: неизвестный результат запроса к
Telegram больше не повторяется автоматически, а прерванная worker-ом отправка
после перезапуска переводится в `unknown`; JSON API читает тело потоково с
лимитом и отклоняет cross-site mutation-запросы.

## Проверенные границы

- **Секреты и клиентский код.** `.env` исключён из Git и Docker-контекста.
  Telegram-токен, webhook secret, пароль админки и операторский chat ID читаются
  только на сервере. `deploy/audit-client-bundle.mjs` просканировал 63 публичных
  файла после production build и не нашёл секретов или token-подобных строк.
- **Админка.** Пароль хранится как scrypt-хеш, сессия — как хеш случайного
  токена. Cookie HttpOnly/SameSite, сессии истекают и отзываются при смене
  пароля, семь неверных попыток закрывают вход на 15 минут. Серверные функции
  повторно проверяют сессию; операции записи защищены CSRF middleware и
  проверкой same-origin.
- **Mini App.** Сервер принимает только сырой `Telegram.WebApp.initData`,
  проверяет HMAC, `auth_date`, формат user и тестовый allowlist. В cookie лежит
  только непрозрачный токен, в базе — его SHA-256; сессия ограничена окружением,
  владельцем Telegram-профиля и сроком 30 дней. Заявки и ссылки на диалог
  проверяют владение и используют идемпотентные ключи.
- **Webhook.** Секрет сравнивается timing-safe до чтения тела; тело ограничено
  256 KiB, JSON и Telegram update проходят строгую схему, принимаются только
  private chat и разрешённые окружения. Повторный `update_id` и callback нельзя
  обработать повторно.
- **Операторский режим.** Нужны одновременно Telegram user ID и подтверждённый
  private chat ID. Callback одноразовый, короткоживущий, привязан к оператору,
  окружению, выбранному диалогу и версии сессии; адресат ответа повторно
  сверяется перед постановкой в outbox.
- **Данные и ввод.** SQL-запросы используют параметры. Пользовательский текст
  выводится React без HTML-инъекций. Медиа проверяется по содержимому, размеру,
  габаритам и хешированному имени; путь к файлу принимает только собственный
  hex-формат.
- **Развёртывание.** Подготовлены непривилегированный systemd-процесс,
  `NoNewPrivileges`, `ProtectSystem`, отдельный каталог данных, права 750,
  резервная копия SQLite и Nginx-конфигурация с очищенными
  `X-Forwarded-For`/`CF-Connecting-IP`.
- **Сбой доставки.** Подтверждённый временный ответ Telegram повторяется по
  backoff; timeout, network reset, неполный ответ и прерванный worker считаются
  неопределёнными и не создают слепной дубль сообщения.

## Условия перед production

1. Запускать приложение только за HTTPS и Nginx; порт Node не должен быть
   доступен из интернета напрямую. Для production использовать длинный
   случайный `TELEGRAM_WEBHOOK_SECRET`, а не короткое значение.
2. Сохранить проверку forwarded-заголовков из шаблона Nginx. Если приложение
   выставляется за другой прокси, он должен сам удалять входящие forwarded
   заголовки и задавать их заново.
3. Перед регистрацией webhook выполнить
   `node deploy/check-telegram-webhook.mjs https://itagent.ru`, затем отдельно
   проверить Mini App, webhook и операторский private chat реальными тестовыми
   сообщениями.
4. При выпуске HTTPS-сертификата убедиться, что Certbot добавил
   `Strict-Transport-Security`; остальные защитные заголовки уже входят в
   `deploy/nginx-itagent.conf` (`X-Content-Type-Options`, `Referrer-Policy`,
   Permissions-Policy и запрет framing). Это deployment hardening, а не обход
   серверной авторизации приложения.
